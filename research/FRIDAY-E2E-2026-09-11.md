## Root causes of the observed failures

### #73

#73 was an over-scoped R1 project request: a Bitcoin-compatible fork with many coupled phases and no bounded, evidence-shaped outcome. The mailbox could admit and run it, but the task semantics were too broad for a single bounded execution. The correct response is not “retry”; it is a smaller feasibility contract. This draft would prevent recurrence only if Project Office/Founder Charter gates replace the original unbounded task with a bounded objective. The runner alone does not.

### #75

#75 narrowed the objective but introduced a strict model/provider requirement: GPT-5.6 Luna only, one verdict, mandatory extra mile, and a bound outcome path. The observed failure was capability/model mismatch (the runtime selected a different model/provider), not ordinary code friction. This draft's capability-card and fail-closed provider boundary would diagnose/refuse the mismatch; it would not make that model available. It prevents silent acceptance, not the underlying missing capability.

### #77

#77 exposed two distinct blockers: local Gemma execution timed out, while external Gemini required human auth. The local timeout is runtime/resource friction; the external path is a genuine authority/capability boundary. PR #117 makes local/public routing and queued auth-required state explicit; PR #123 makes Gemini fail closed and emits `AUTH_REQUIRED`. Neither guarantees useful local throughput under real latency, and neither provides the durable settlement/export surface identified by PR #81.

## What this draft still misses

1. **Role lease vs task lease.** #121 proves a multi-hour commander mandate is not represented by the mailbox. A task process ending can terminate the only control loop even while the role's deadline remains. The smallest architectural primitive is a deadline-bound `RoleLease/CommanderLease` that survives subordinate task settlement and stops on deadline, revoke, budget exhaustion, or sovereign boundary. Subtasks keep strict ordinary settlement.

2. **Monotonic recovery.** PR #81's exact implementation can freeze the first ledger decision: `checkpoint_only` does not advance when a correctly bound outcome later appears. Idempotency must mean “same semantic effect at most once,” not “never reconsider a now-provable transition.”

3. **Durable evidence before settlement.** Local checkpoint files are insufficient when the reporter cannot see the run directory. Publication/export must create a repository-controlled, identity-bound evidence checkpoint before reporter classification; publication must not become completion authority.

4. **Evidence acceptance safety.** Hashes and task/lease binding prevent obvious stale-task substitution, but they do not prove that an artifact answers the intended objective. The reporter needs an explicit outcome schema with semantic objective ID, producer, provenance, required fields, and independent validation. “Any file with a matching hash” is unsafe.

5. **Settlement is not project status.** Project Office's `PROJECT_STATUS` is a semantic/investor-style state, while mailbox receipts are execution/settlement state. They must be linked by evidence references, not collapsed into one green status.

6. **No real quota telemetry.** The release records only the user-supplied observation (weekly ~85%, ~1 percentage point over roughly half a day, 5-hour meter unknown, emergency ceiling +5pp) and the exposed model/provider facts above. No token or quota number is invented.
