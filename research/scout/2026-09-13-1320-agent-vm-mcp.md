# Research Scout — agent-vm-mcp control-plane pattern

Date: 2026-09-13
Status: finding only; NO-OP on execution / no candidate Issue created

## Evidence

Fresh repository created 2026-09-13: https://github.com/DevilTea/agent-vm-mcp

Upstream describes an MCP control plane for a **dedicated Linux agent VM** with finite shell execution, bounded file operations, isolated Git worktrees, persistent coding-agent orchestration via Herdr, optional upstream MCP bridging, read-only system audit, artifact handling, and an OpenAI Secure MCP Tunnel deployment guide.

Two implementation ideas are directly relevant to our mailbox/router work:

1. **Submission certainty is separate from retry safety.** `agent_prompt` distinguishes `not_submitted` (safe to retry) from `possibly_submitted` (do not auto-retry). This is a stronger idempotency primitive than treating timeout/cancellation as failure.
2. **Tool-catalog identity is explicit.** `server_info` returns a deterministic SHA-256 identity of the active MCP action catalog and compares it with the marker embedded in the host-fetched tool definition, detecting stale host snapshots after server/tool changes.

The repo is extremely new and currently has 0 stars / 0 forks, so there is no adoption signal yet.

## Decision-relevant negative finding

Do **not** treat this project as an authorization/security boundary. Upstream explicitly states that access is shell-equivalent and that **the VM itself is the trust boundary**; it is not a sandbox, multi-tenant isolation layer, or authorization broker. A trusted process inside the VM is assumed capable of reaching everything available to that Linux user.

Therefore it is not a replacement for our mailbox authority / SecurityManager / mutation-boundary model. It could only sit **below** those controls, as a disposable or dedicated execution substrate.

## Reusable patterns to steal without adopting the repo

- Extend mailbox execution receipts with `submission_state ∈ {not_submitted, possibly_submitted, submitted/known}` and derive `retry_safe` deterministically rather than from transport errors.
- Bind MCP/router executions to a `tool_catalog_hash` / schema-version commitment so a task cannot silently execute against a different tool surface than the allocator/reviewer saw.
- Preserve the stronger rule: `VM reachability != execution authority`; VM isolation limits blast radius but does not grant permission.

## Option-value assessment

**Medium, monitor/defer.** The patterns are high leverage and cheap to copy conceptually, but the upstream repository is too young for an adoption candidate and overlaps existing secure-tunnel / VM work. No new Issue is justified yet.
